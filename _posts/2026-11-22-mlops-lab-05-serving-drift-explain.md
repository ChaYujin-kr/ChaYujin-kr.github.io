> **요약** 서버가 200을 돌려주고, 드리프트 점수가 나오고, 설명이 출력됐다. 셋 다 동작했다. 그리고 셋 다 대조군을 두고 다시 재 보니 처음 본 것과 다른 이야기였다.
{: .prompt-tip }

11장은 세 부분이다. 10장에서 등록한 추천 모델을 서빙하고, 데이터 드리프트를 감지하고, 추천에 이유를 붙인다.

## 1. 서빙

서비스는 시작할 때 MLflow에서 별칭이 `prod`인 모델을 받아 온다. 띄우기까지 세 번 막혔다.

| 시도 | 오류 | 원인 |
|---|---|---|
| 1 | `DuplicateTimeseries: ... ranked_movie_present_counter` | 카운터 두 개의 이름이 같음 |
| 2 | `Registered model alias prod not found` | 파이프라인은 `staging`까지만 붙임 |
| 3 | `TypeError: code expected at most 16 arguments, got 18` | 모델을 저장한 Python과 읽는 Python이 다름 |

### 이름이 같은 카운터

```python
ranked_movie_present_counter = Counter(name="ranked_movie_present_counter", ...)
ranked_movie_absent_counter  = Counter(name="ranked_movie_present_counter", ...)
```

복사해서 붙인 뒤 이름을 고치지 않은 것이다. Prometheus는 같은 이름의 지표를 두 번 등록하지 못하게 해서 서버가 뜨지 않는다.

### `staging`과 `prod` 사이

10장의 파이프라인은 검증을 통과한 모델에 `staging` 별칭을 붙인다. 서비스는 `prod`를 찾는다. 그 사이를 잇는 코드는 없다.

빠진 것이 아니라 의도라고 봤다. 6~7장 실습에서 챔피언 교체를 사람 손에 남겨 둔 것과 같은 구조다. 여기서는 별칭을 직접 붙였다.

```python
client.set_registered_model_alias("recommender_production", "prod", "1")
```

### 모델 파일은 Python 버전에 묶인다

```
TypeError: code expected at most 16 arguments, got 18
```

`torch.load` 안에서 났다. 모델 클래스 `MatrixFactorization`은 학습 컴포넌트 함수 **안에** 정의돼 있다. 불러올 수 있는 모듈에 있는 것이 아니라서, MLflow는 클래스의 코드 자체를 모델 파일에 함께 담는다. 이 코드는 Python 바이트코드이고, 바이트코드 형식은 버전마다 다르다.

10장에서 컴포넌트 이미지를 `python:3.11`로 고정했는데 서빙 환경은 3.10으로 만들었다. 모델과 같이 저장된 파일에 답이 적혀 있었다.

```bash
cat model/python_env.yaml
# python: 3.11.18
```

서빙 환경을 3.11로 다시 만들자 떴다. 모델 클래스를 함수 안에 두면 편하지만, 그 모델은 학습 때의 Python 버전에서만 읽을 수 있게 된다.

### 떴다. 그런데 무엇을 추천하는가

```bash
curl -s -X POST localhost:3001/predict -H 'Content-Type: application/json' \
  -d '{"user_id": 1, "top_k": 5}'
# [18230, 77224, 99308, 121704, 3717]   200, 0.2초
```

응답도 빠르고 모양도 맞다. 이 번호들이 실제 영화인지 `movies.csv`와 대조했다. 사용자 50명에게 10개씩 추천을 받았다.

| 항목 | 값 |
|---|---|
| 추천된 ID | 500개 |
| 실제로 있는 영화 | 29개 (5.8%) |
| ID 범위(1~193,609)에서 실제 영화의 비율 | 5.0% |

**추천의 94%가 존재하지 않는 영화다.** 5.8%는 아무 번호나 뽑았을 때의 5.0%와 거의 같다.

원인은 ID가 띄엄띄엄하다는 데 있다. 영화는 9,742편인데 가장 큰 ID가 193,609다. 모델은 가장 큰 ID에 맞춰 임베딩 표를 19만 행으로 만들고, 서비스는 1번부터 끝 번호까지 모두를 후보로 놓고 점수를 매긴다. 학습 데이터에 한 번도 나오지 않은 18만 행은 초깃값 난수 그대로이고, 그중에서 우연히 큰 점수가 상위를 차지한다.

번호도 한 칸 어긋나 있다. 학습은 `movieId - 1`을 임베딩 번호로 쓰는데 서비스는 후보 번호를 빼지 않고 그대로 넣는다. 그래서 한 칸 옮겨서도 대조해 봤지만 24개로 마찬가지였다.

고치려면 두 가지가 필요하다. 영화 ID를 0부터 빈틈없는 번호로 다시 매기고, 후보를 실제 목록에 있는 영화로 제한해야 한다. 이번 실습에서는 고치지 않고 확인까지만 했다.

없는 사용자 ID(99999)를 보내면 500과 `IndexError: index out of range`가 난다. 입력 검증도 없다.

`/readyz` 200, `/predict` 200, 응답 0.2초. 운영 지표로는 모두 정상이다. 9장에서는 "실제 입력을 보내 봐야 한다"고 썼는데, 여기서는 한 걸음 더 가야 했다. **응답의 내용이 말이 되는지** 봐야 한다.

## 2. 드리프트

책의 노트북은 이렇게 진행한다.

1. 평점 데이터로 모델 A를 학습한다.
2. 일부 영화(ID 1~100)의 평점을 1점씩 올려 "취향이 바뀐" 데이터를 만든다.
3. 그 데이터로 모델 B를 학습한다.
4. 두 모델의 아이템 임베딩을 deepchecks의 `FeatureDrift`로 비교한다.

원본 데이터가 아니라 **모델이 배운 표현**이 달라졌는지를 보는 방식이다.

### 노트북의 두 데이터는 같은 데이터였다

```python
def introduce_user_drift(df, movie_ids, drift_amount=1):
    drift_indices = df['movieId'].isin(movie_ids)
    df.loc[drift_indices, 'rating'] = df.loc[drift_indices, 'rating'] + drift_amount
    ...
    return df

movie_ratings_with_drift = introduce_user_drift(ratings_df, action_movie_ids)
```

함수가 받은 `df`를 그 자리에서 고치고 그대로 돌려준다. `ratings_df`와 `movie_ratings_with_drift`는 이름만 둘이고 같은 객체다.

```
원본과 드리프트 데이터가 같은 객체인가: True
두 데이터에서 값이 다른 평점 수: 0
```

모델 A도 B도 드리프트가 들어간 데이터로 학습된다. `.copy()`를 넣으면 1만 건 중 1,170건이 달라지고 평균 평점이 3.559에서 3.676으로 오른다.

### 그런데 고쳐도 점수가 같다

네 가지 조건으로 다시 쟀다. 점수는 Kolmogorov-Smirnov 통계량이고 클수록 두 분포가 다르다는 뜻이다.

| 조건 | 노트북이 보는 열 | 평점 올린 영화 100편 평균 | 건드리지 않은 영화 100편 평균 |
|---|---|---|---|
| A. 노트북 그대로 (같은 데이터) | 0.150 | 0.258 | 0.229 |
| B. 복사본으로 고침 | 0.200 | 0.263 | 0.258 |
| C. 대조군: 같은 원본 데이터, 시드만 다름 | 0.250 | 0.250 | 0.247 |
| D. 원본과 드리프트 데이터, 시드는 같음 | 0.050 | 0.049 | 0.050 |

읽는 법은 이렇다.

- **A와 B가 비슷하다.** 드리프트가 있든 없든 점수가 0.25 근처다.
- **C가 결정적이다.** 데이터가 완전히 같은데 시드만 달라도 0.25가 나온다.
- **D에서 사라진다.** 데이터가 다른데 시드를 맞추면 0.05로 떨어진다. 평점을 올린 영화와 그렇지 않은 영화의 차이도 없다.

이 점수는 데이터의 변화가 아니라 **두 모델의 초깃값이 다르다는 것**을 재고 있다.

이유도 숫자로 나온다. 임베딩 초깃값의 표준편차는 1인데, 5 에폭 학습으로 임베딩이 움직인 평균 크기는 0.00003이었다. 학습률 0.001의 SGD로는 임베딩이 출발점에서 거의 움직이지 않는다. 비교한 것은 사실상 난수 두 벌이다.

표본 수도 작다. 노트북은 임베딩 행렬을 뒤집어서 열 하나를 영화 하나로 놓는다. 그러면 열 하나의 표본은 임베딩 차원 수인 20개다. 20개짜리 두 표본의 KS 통계량은 같은 분포에서 뽑아도 0.2~0.3이 흔히 나온다.

### 여기서 배운 것

6~7장 실습의 결론은 "드리프트 경보가 곧 성능 저하는 아니다"였다. 이번에는 그 앞 단계다. **경보 자체가 무엇을 재고 있는지**부터 확인해야 한다.

방법은 대조군이다. 드리프트가 없는 두 표본으로 같은 검사를 돌려서 점수가 얼마나 나오는지 본다. 그 값이 드리프트를 넣었을 때와 같다면 검사는 아무것도 구별하지 못하고 있는 것이다. 네 조건을 모두 돌리는 데 몇 분이면 됐다.

임베딩을 비교하려면 최소한 두 가지는 맞춰야 한다. 두 모델을 같은 초깃값에서 시작하거나 이전 모델에서 이어서 학습할 것, 그리고 임베딩이 실제로 움직일 만큼 학습할 것.

## 3. 설명 가능성

마지막은 EMF(Explainable Matrix Factorization)다. 추천마다 "나와 취향이 비슷한 이웃 10명 중 몇 명이 이 영화에 몇 점을 줬는가"를 붙인다.

```
userId  itemId  rank        explanations
   1.0   474.0   1.0  {3: 1, 4: 4, 5: 4}
   1.0  1449.0   2.0                  {}
   1.0   408.0   3.0        {4: 2, 5: 4}
```

1번 사용자의 1순위 추천(474번)은 이웃 9명이 봤고, 4명이 5점, 4명이 4점, 1명이 3점을 줬다. 2순위(1449번)는 설명이 비어 있다. 이웃 중 아무도 보지 않은 영화다.

| 항목 | 값 |
|---|---|
| 데이터 | ml-100k (사용자 943명) |
| 학습 시간 (10 에폭) | 230초 |
| 추천 수 | 9,430 (1인당 10개) |
| 설명이 빈 추천 | 52.4% |

추천의 절반은 이유를 댈 수 없다. 노트북의 설정이 `expl_reg_term=0.0`이기 때문이다. 이 값은 "이웃이 좋게 본 영화 쪽으로 임베딩을 끌어당기는 힘"인데, 0이면 꺼진 것이고 모델은 보통의 행렬 분해와 같다. 설명은 추천이 끝난 뒤에 덧붙여질 뿐이다.

값을 0.1로 올려 한 번 더 돌렸다.

| `expl_reg_term` | 설명이 빈 추천 | 추천당 근거가 되는 이웃 수 | 마지막 에폭 학습 MSE |
|---|---|---|---|
| 0.0 | 52.4% | 2.04명 | 0.779 |
| 0.1 | 42.2% | 2.67명 | 0.845 |

설명할 수 있는 추천이 10%p 늘고 오차는 커졌다. 설명 가능성과 정확도를 맞바꾸는 손잡이다. 각 조건을 한 번씩만 돌린 결과라서 차이의 크기까지 믿을 수는 없고, 방향만 본다.

## 정리

- 모델 클래스를 함수 안에 정의하면 모델 파일이 Python 버전에 묶인다. `python_env.yaml`에 적혀 있다.
- 200 응답과 빠른 속도는 답이 맞다는 뜻이 아니다. 추천된 ID가 실제 목록에 있는지 대조한다.
- 띄엄띄엄한 ID를 그대로 임베딩 번호로 쓰지 않는다.
- 제자리에서 고치는 함수는 원본도 바꾼다. 비교 실험에서는 `.copy()`.
- 검사를 믿기 전에 대조군을 돌린다. 변화가 없을 때의 점수를 먼저 안다.
- "설명 가능한 모델"이라도 설정에 따라 설명은 사후에 붙인 장식일 수 있다.
