> **요약** 3편의 "전문 넣기"는 캐시 할인을 전제로 한 선택이었다. 실제 방문은 드문드문이라 캐시가 자주 식었다. 블록 검색으로 바꾸고 입력 토큰이 약 1/4이 됐다.
{: .prompt-tip }

## 문제: 평가 때와 실제가 달랐다

3편에서 전문을 넣어도 싸다고 본 근거는 캐시 비율 99%였다. 그런데 그건 **평가 스크립트가 질문을 연달아 보냈기 때문**이었다. 실제 기록을 보니 이랬다.

| 기록 | 입력 토큰 | 캐시 | 질문당 비용 |
|---|---|---|---|
| #4 | 12,391 | 0 | 약 $0.0105 |
| #5 | 12,391 | 0 | 약 $0.0105 |
| #6 | 12,391 | 12,288 | 약 $0.0023 |

캐시는 몇 분 동안 같은 요청이 없으면 사라진다. 방문자가 드문드문 오는 블로그에서는 대부분 식은 상태다. 게다가 이 시리즈 10편이 추가되면 전문이 **약 2.3만 토큰**으로 두 배가 될 참이었다.

## 한 일

### 블록 DB를 블로그 빌드가 만든다

```text
글 푸시 → GitHub Actions(블로그 빌드) → 빌드된 HTML을 ## 단위로 자름 → assets/data/blocks.json
```

- 블록마다 `글 slug, 블록 id, 제목, 태그, 요약, 본문`.
- **요약은 본문 앞 100자를 그대로 자른 것**이다. LLM으로 요약하지 않았다. 비용이 0원이고 블로그 저장소에 API 키를 둘 필요가 없다.
- 블록 id는 **빌드된 HTML의 제목 id**를 그대로 쓴다. 블로그 앵커와 항상 같다.

게이트웨이는 이 파일을 블로그 주소에서 읽어 10분 동안 기억한다. 그래서 **글을 써도 게이트웨이를 다시 배포할 필요가 없다.** 못 읽으면 배포 때 묶어 둔 옛 코퍼스로 답한다.

### 검색한 블록만 넣는다

질문으로 블록을 검색(BM25, 글자 2개 조각)해서 상위 6개만 넣는다. 목차는 그대로 넣어서, 검색이 놓쳐도 "이 글을 참고하라" 정도는 할 수 있다.

## 문제: 처음엔 글 1편만 읽혔다

블록 생성 스크립트를 실제 블로그 HTML에 돌렸더니 22편 중 1편만 나왔다. 이어서 고쳤더니 이번엔 **글마다 마지막 블록이 빠졌다.**

| 증상 | 원인 | 해결 |
|---|---|---|
| 1편만 읽힘 | `<img/>` 같은 자기 닫힘 태그를 "열고 닫힘"으로 두 번 세서 본문 깊이가 어긋남 | 깊이를 세지 않고, 본문 구간을 문자열로 먼저 잘라 냄 |
| 마지막 블록 누락 | 빌드된 HTML은 압축돼 `</li>`, `</td>` 같은 닫는 태그가 **생략**됨. 코드 줄번호 칸(`<td>`)을 건너뛰다 끝을 못 찾음 | 칸은 "다음 칸이 시작되거나 줄이 끝나면" 건너뛰기 종료 |

마지막으로 기존 코퍼스와 블록 id를 글마다 대조해 **전부 같은 것**을 확인했다.

## 결과

| | 입력 토큰 | 질문당 비용(캐시 없음) |
|---|---|---|
| 전문 넣기 | 12,391 | 약 $0.0105 |
| 블록 검색 | 2,000~3,200 | 약 $0.0017~0.0036 |

블로그 밖 질문("주인장 학교", "너의 이름은")은 그대로 거절했다.

> 정답 세트로 다시 채점하는 검증은 **일부러 하지 않았다.** 11/8 실험에서 같은 방식이 인용 93%(전문 100%)였고, 그 정도 차이를 돈 들여 다시 재기보다 실제 질문을 보며 고치기로 했다.
{: .prompt-info }

## 정리

- 평가 환경의 숫자(캐시 99%)를 운영 숫자로 착각하지 말 것. 실제 기록으로 다시 본다.
- 데이터가 바뀌는 쪽(블로그)이 인덱스를 만들게 하면, 서빙 쪽은 배포 없이 따라온다.
