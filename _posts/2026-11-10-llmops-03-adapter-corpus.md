> **요약** 글이 수십 편이면 검색(RAG)보다 전문을 넣는 쪽이 정확하고 싸다. 모델에게는 URL을 쓰게 하지 않고 "몇 번 단락"만 고르게 했다.
{: .prompt-tip }

## 얇은 어댑터

OpenAI와 Gemini를 같은 함수 하나로 부르게 했다.

```python
result = provider.generate(system, user, schema=SCHEMA)   # 어느 제공사든 같은 모양
```

- 공식 SDK 없이 HTTP를 직접 호출한다. 의존성이 `httpx` 하나라 해시 고정과 SBOM이 단순해진다.
- **OpenAI 호환 형식**을 기준으로 삼았다. vLLM·Ollama 같은 온프렘 서버도 같은 형식이라 나중에 주소만 바꾸면 된다.
- 모델은 `gpt-5.4-mini-2026-03-17`처럼 **날짜 붙은 이름**으로 고정한다. 별칭은 제공사가 가리키는 모델을 바꿀 수 있다.

## 코퍼스: 단락마다 id

블로그 글을 제목(`##`) 단위로 쪼개고, 블로그의 앵커와 같은 id를 붙였다.

```json
{ "slug": "mlops-drift-07-judge-rule-failed",
  "sections": [{ "id": "라벨을-확인했더니", "heading": "라벨을 확인했더니", "text": "..." }] }
```

id가 실제 블로그 앵커와 같은지 스크립트로 전부 대조했다. 링크를 눌렀는데 엉뚱한 곳으로 가면 근거 링크가 의미가 없다.

## RAG 대신 전문

| | 검색(RAG) | 전문 넣기 ✅ |
|---|---|---|
| 정확도 | 검색이 틀리면 엉뚱한 단락만 들어감 | 검색 실패가 없음 |
| 비용 | 입력이 적음 | 질문당 약 1.2만 토큰. 하지만 앞부분이 매번 같아 **캐시 할인** |
| 한계 | 글이 많아도 됨 | 글이 수백 편이 되면 못 씀 |

프롬프트 순서를 **[지시문 → 블로그 전문 → 질문]** 으로 둔 이유가 캐시다. 앞부분이 같아야 할인이 걸린다. OpenAI에서 캐시 비율은 99%였다. 검색 버전도 만들어서 비교해 두었다. 글이 많아지면 그때 바꾼다.

## 링크는 코드가 만든다

모델의 답은 JSON 스키마로 강제했다.

```json
{ "can_answer": true, "answer": "...", "citations": [{ "post": "...", "section": "..." }] }
```

모델은 **코퍼스에 있는 id만** 고른다. URL은 우리 코드가 id로 조립한다. 없는 id를 고르면 버리고, 남은 근거가 0개면 답 자체를 "찾지 못했어요"로 바꾼다.

이렇게 하면 인젝션으로 모델이 넘어가도 **외부 주소를 내보낼 길이 없다.** 1편의 Rule of Two에서 "외부 전송"을 지운 장치가 이것이다.

## 정리

- 어댑터는 얇게, 형식은 OpenAI 호환으로. 교체 비용이 낮아진다.
- 규모가 작으면 단순한 쪽(전문 넣기)이 정확하고, 캐시 덕에 싸다.
- 모델이 쓰는 URL을 믿지 않는다.
