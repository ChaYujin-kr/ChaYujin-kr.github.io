> **요약** 다섯 번째 실행에서 성공했다. 네 번의 실패는 모두 모델과 상관없는 환경 문제였다. 메모리 상한을 걸어 두지 않은 한 번은 노트북 전체를 멈추게 했다.
{: .prompt-tip }

8장은 7장의 데이터 준비 뒤에 YOLOv8 학습과 검증을 붙인다. 단계는 `내려받기 → 분할 → 학습 → 검증` 네 개다.

환경은 메모리 7.7GB짜리 노트북의 kind 클러스터다. GPU(GTX 1060 6GB)가 있지만 kind 안에서는 쓰지 않으므로 파이프라인의 학습은 CPU로 돈다.

## 실행 기록

| 실행 | 결과 | 원인 |
|---|---|---|
| 1 | 실패 (683초) | `libgl1-mesa-glx` 패키지가 없음 |
| 2 | 실패 (617초) | `cannot import name 'YOLO'` |
| 3 | WSL 재시작 | 메모리 부족으로 추정 |
| 4 | 실패 (518초) | `OOMKilled` (상한 3G) |
| 5 | 성공 (505초) | 배치 2, 워커 0 |

캐시를 켜 두어서, 한 번 성공한 내려받기와 분할 단계는 코드를 바꾸지 않는 한 다시 돌지 않았다. 실패 시간의 대부분은 이미지를 받는 시간이었다.

## 1. 없어진 패키지

책의 학습 단계는 `python:3.11-slim` 이미지를 띄운 뒤 실행할 때마다 `apt-get`과 `pip`로 필요한 것을 설치한다.

```
E: Package 'libgl1-mesa-glx' has no installation candidate
python3: can't open file '/train.py': [Errno 2] No such file or directory
```

`python:3.11-slim`의 바탕이 Debian 13(trixie)으로 바뀌었고, 이 패키지는 거기서 없어졌다. 3장에서 겪은 것과 같은 종류의 문제다. 태그는 그대로인데 내용이 바뀐다.

패키지 이름만 `libgl1`로 고치는 방법도 있지만, 실행할 때마다 설치하는 구조 자체를 바꿨다. 검증 단계가 이미 쓰고 있는 `ultralytics/ultralytics:8.3.56-cpu` 이미지를 학습에도 썼다. 설치 단계가 없어지고, 학습과 검증의 라이브러리 버전도 같아진다.

## 2. 이름이 겹친 폴더

이미지를 바꾸자 다른 오류가 났다.

```
ImportError: cannot import name 'YOLO' from 'ultralytics' (unknown location)
```

`ultralytics`가 설치된 이미지에서 `ultralytics`를 못 불러온다는 말이다. `(unknown location)`이 단서였다. 같은 이미지로 Pod를 하나 띄워 직접 확인했다.

```bash
kubectl run ultra-check --rm -i --restart=Never \
  --image=ultralytics/ultralytics:8.3.56-cpu -- bash -c '
  echo "import sys, ultralytics; print(sys.path[0], ultralytics.__file__, list(ultralytics.__path__))" > /t.py
  python3 /t.py; cp /t.py /tmp/t.py; python3 /tmp/t.py'
```

```
/    None                                   ['/ultralytics']
/tmp /ultralytics/ultralytics/__init__.py   ['/ultralytics/ultralytics']
```

파이썬은 실행하는 스크립트가 있는 폴더를 검색 경로 맨 앞에 넣는다. 스크립트가 `/train.py`이면 그 폴더는 `/`다. 그런데 이 이미지에는 소스 폴더 `/ultralytics`가 있다. 파이썬은 진짜 패키지(`/ultralytics/ultralytics`)보다 먼저 이 껍데기 폴더를 `ultralytics`로 잡았다. 스크립트를 `/tmp/train.py`에 두면 해결된다.

## 3. 노트북이 멈췄다

세 번째 실행에서는 학습이 시작된 뒤 WSL이 통째로 재시작됐다. 당시 로컬에서 다른 실습 스크립트도 함께 돌리고 있었다.

재시작으로 로그가 지워져 원인을 확정하지는 못했다. 남은 정황은 이렇다.

- 재시작 직전 `free -h`의 여유 메모리가 129MB였다.
- 함께 돌던 스크립트의 에폭당 시간이 25초에서 101초로 늘었다.
- 같은 시각 다른 파이프라인의 `pip install`이 연결 오류로 실패했다.

학습 Pod에는 메모리 상한이 없었다. 상한이 없는 Pod는 노드의 메모리를 다 쓸 수 있고, kind에서는 그 노드가 곧 내 노트북이다.

## 4. 상한을 걸고 다시

```python
train_op.set_memory_limit('3G')
```

이번에는 학습 첫 배치에서 Pod만 죽었다.

```
yolo-object-detection-pipeline-...-impl-2893688001   OOMKilled
```

결과는 같은 실패지만 의미가 다르다. 클러스터와 노트북은 멀쩡했고, 원인이 Pod 상태에 그대로 적혀 있다. 3번의 재시작도 메모리였을 가능성이 높아졌다.

필요한 메모리가 얼마인지는 로컬에서 쟀다.

```bash
/usr/bin/time -f "peak_rss_mb=%M" python train_small.py   # CPU, 워커 0, 데이터 10%
```

| 배치 크기 | 최대 메모리 |
|---|---|
| 8 | 2.98GB |
| 2 | 1.26GB |

배치 8은 학습 프로세스 하나만으로 3G에 닿는다. 여기에 기본값인 데이터 로더 워커 8개가 더해진다. 배치 2, 워커 0으로 줄였다.

## 5. 성공

| 항목 | 값 |
|---|---|
| 전체 | 505초 (내려받기·분할은 캐시) |
| 학습 1 에폭 (CPU) | 292초 |
| mAP50 | 0.995 |
| mAP50-95 | 0.934 |

비교하려고 같은 데이터를 로컬 GPU로도 학습했다.

| | 파이프라인 (CPU) | 로컬 (GTX 1060) |
|---|---|---|
| 에폭당 시간 | 292초 | 약 21초 |
| 10 에폭 뒤 mAP50-95 | (1 에폭만 실행) | 0.995 |

에폭당 14배 차이다. 파이프라인으로 옮긴다고 학습이 빨라지지는 않는다. 얻는 것은 반복 가능성과 기록이다.

## 라벨 어긋남은 어디를 망가뜨렸나

7장에서 이미지와 라벨이 다른 묶음으로 흩어지는 문제를 찾았다. 영향을 재려고 원본 파이프라인이 만든 파일 목록을 그대로 로컬에 재현해 GPU로 10 에폭씩 학습했다.

| 학습 데이터 | 평가 데이터 | mAP50 | mAP50-95 |
|---|---|---|---|
| 어긋남 (427장 중 325장만 라벨 있음) | 올바른 라벨 143장 | 0.995 | 0.995 |
| 올바름 (427장 모두 라벨 있음) | 올바른 라벨 143장 | 0.995 | 0.995 |
| 올바름 | **어긋난 검증 세트** (85장 중 14장만 라벨 있음) | 0.164 | 0.164 |

예상은 "학습 데이터의 4분의 1이 틀렸으니 모델이 나빠진다"였다. 결과는 달랐다. 학습 쪽은 차이가 없었다. 라벨이 없는 이미지는 "물체 없음"으로 처리되는데, 이 데이터는 그 정도 잡음으로는 흔들리지 않을 만큼 쉬웠다.

망가진 곳은 평가였다. 멀쩡한 모델을 어긋난 검증 세트로 재면 mAP50이 0.995에서 0.164로 떨어진다. 모델이 카드를 제대로 찾아도, 그 이미지에 라벨이 없으니 전부 오탐으로 계산된다(정밀도 0.165, 재현율 1.000).

만약 원본 파이프라인이 끝까지 돌았다면 "모델 성능이 나쁘다"는 숫자를 받았을 것이고, 원인을 모델이나 에폭 수에서 찾았을 것이다. 실제 원인은 정렬 한 줄이었다.

### 확인하지 못한 가설 하나

파일 이름이 `CA01_07.tif`처럼 생겼다. `CA01`이 영상 하나이고 프레임이 30장씩 있다. 무작위로 나누면 같은 영상의 프레임이 학습과 검증에 함께 들어가니 점수가 부풀려졌을 것이라고 의심했다.

영상 단위로 나눠(학습 14개, 검증 3개, 테스트 2개) 다시 학습했다. 결과는 mAP50-95 0.995로 같았다. 이 데이터에서는 누수의 영향이 보이지 않았다. 어려운 데이터라면 달랐을 수 있지만, 여기서 잰 숫자로는 주장할 수 없다.

## 고친 것

| 변경 | 이유 |
|---|---|
| 분할 단계에서 목록 정렬 + 짝 검사 | 이미지와 라벨 어긋남 |
| 학습 이미지를 `ultralytics/ultralytics:8.3.56-cpu`로 | 실행 중 설치 제거, 검증과 버전 통일 |
| 스크립트 위치를 `/tmp/train.py`로 | `/ultralytics` 폴더와 이름 충돌 |
| `workers=0`, 배치 2 | 메모리 |
| `set_memory_limit('3G')` | 넘치면 Pod만 죽게 |

## 정리

- 실행할 때 설치하는 단계는 언젠가 깨진다. 이미지에 고정한다.
- `(unknown location)`이 보이면 같은 이름의 폴더가 검색 경로에 있는지 본다.
- 로컬 클러스터의 무거운 단계에는 메모리 상한을 건다. `OOMKilled`는 원인을 알려 주지만, 멈춘 노트북은 아무것도 알려 주지 않는다.
- 필요한 메모리는 추측하지 말고 `/usr/bin/time`으로 잰다.
- 점수가 이상하면 모델보다 평가 데이터를 먼저 의심한다.
